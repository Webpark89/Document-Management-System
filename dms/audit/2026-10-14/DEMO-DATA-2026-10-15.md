# ผลการแทนที่ข้อมูลเอกสารสำหรับสาธิต — 15 ตุลาคม 2569

นำข้อมูลลง PostgreSQL ของแอปจริงเรียบร้อยแล้ว: ฐานข้อมูล `dms_oldDB`, schema `public` บน localhost:5433

Batch: `dms_demo_1792056971291_80d3cf`

## ขอบเขตและข้อมูลที่เก็บไว้

- สำรองและแทนที่เอกสารเดิม 130 ฉบับ รวมข้อมูลฟอร์ม ไฟล์เวอร์ชัน workflow โฟลเดอร์ และประวัติ/การแจ้งเตือนที่ผูกกับเอกสารเดิม
- ตรวจ fingerprint ของทั้งแถวก่อนและหลัง: ผู้ใช้ 8 บัญชี, roles 6, permissions 108, role permissions 212, departments 5, positions 3, document types 4 และ approval matrix 7 แถว เหมือนเดิมทั้งหมด
- รหัสผ่าน ลายเซ็นในโปรไฟล์ สถานะบัญชี และข้อมูลผู้ใช้ไม่ถูกแก้ไข บัญชีที่ inactive ยังคงอยู่
- เก็บ audit เดิมที่ไม่เกี่ยวกับเอกสารไว้ 32 รายการ พร้อมเพิ่ม audit การแทนที่ข้อมูล 1 รายการ

ข้อมูลครอบคลุมการแก้ไขร่าง การส่งอนุมัติตามรายชื่อและบทบาท อนุมัติบางขั้น อนุมัติครบ ส่งกลับแก้ไข ส่งใหม่ ปฏิเสธ และยกเลิก มี snapshot แต่ละเวอร์ชันและประวัติรอบ workflow เดิม เก็บ PDF คนละไฟล์ตามเหตุการณ์ ไม่ได้สร้างข้อมูลจำลองในหน้าเว็บ

ใช้ผู้สร้าง 6 บัญชีเดิม กระจายงานตามแผนกและกำหนด CompanyWide / Department / SpecificUsers พร้อมโฟลเดอร์ร่วมและสิทธิ์ดู/แก้ไข ไม่มีผู้สร้างอนุมัติเอกสารตัวเอง

ตราลายเซ็นที่สร้างในประวัติจำลองระบุ `DEMO APPROVAL / SAMPLE` และเอกสารมีป้ายข้อมูลจำลอง ไม่ใช่หลักฐานการอนุมัติจริงของเจ้าของบัญชี ลายเซ็นจริงในโปรไฟล์ไม่ได้ถูกคัดลอกหรือแก้ไข

## ผลตรวจ

- อ่านและ parse PDF ครบ 246 ไฟล์จากฐานข้อมูลจริง ขนาดไฟล์ตรง byte ที่เก็บ แต่ละ PDF มี hash แตกต่างกัน
- เลขเวอร์ชันต่อเนื่อง สถานะ snapshot ล่าสุดตรงกับเอกสาร วันที่สร้าง/เวอร์ชันไม่อยู่ก่อนบัญชีเจ้าของหรือหลังเวลาปัจจุบัน
- ไม่พบการอนุมัติเอกสารตัวเอง ผู้อนุมัติผิดบทบาท บัญชีผู้อนุมัติไม่พร้อมใช้งาน หรือไฟล์หาย
- ยอดรวม PR/PO ตรงรายการย่อยในชุดที่เตรียม และนำเข้าชุดเดียวกันตาม SHA-256
- เอกสาร Approved มีทุกขั้นอนุมัติพร้อมวันลงนามและโฟลเดอร์ เอกสาร Pending มีผู้อนุมัติปัจจุบันพร้อมดำเนินการ
- อ่านรายการเอกสารและ Dashboard ผ่าน service จริงครบ 7 บัญชี active สำเร็จ ทุกบัญชีมีข้อมูลตามสิทธิ์
- ทดสอบตัวสร้างเลขจริงใน transaction แล้ว rollback: PR/PO/BK/DOC ได้เลขถัดไป `PREFIX-2026-0017`; counter ใน DB ยังคง 16
- เรนเดอร์และตรวจหน้าตัวอย่าง PDF ทั้ง 4 ประเภท ไม่มีข้อความ/ตราอนุมัติทับกัน
- ลบ schema ชั่วคราวที่ใช้เตรียมข้อมูลทั้ง 3 ชุดแล้ว ไม่เปลี่ยนการตั้งค่าเชื่อมต่อแอป

การตรวจรอบนี้เป็นการตรวจฐานข้อมูล ไฟล์ PDF และ service ของระบบ ไม่ได้สวมสิทธิ์บัญชีหรือสร้าง token เพื่อกดอนุมัติในเบราว์เซอร์

## สำรองและสคริปต์

สำรองข้อมูลก่อนแทนที่ (รวมไฟล์ PDF เดิม):

`server/.local/demo-seed/dms_demo_1792056971291_80d3cf/before-replacement.json.gz`

ไฟล์ `backup-sha256.txt` ใช้ตรวจความสมบูรณ์ของ backup; `manifest.json`, `applied.json`, `quality-check.json`, `primary-quality-check.json` และ PDF ตัวอย่างอยู่ในโฟลเดอร์เดียวกัน เก็บใน `.local` ที่ไม่เข้า Git เนื่องจาก backup มีข้อมูลเอกสารเดิม การกู้คืนต้องใช้ขั้นตอนนำเข้าที่ตรวจสอบความสัมพันธ์ ไม่ใช่นำ `dataset.json.gz` กลับไปรันแทน backup

สคริปต์: `scripts/reseed-document-demo.cjs`

```powershell
# เตรียมชุดใหม่ใน schema แยก และตรวจสอบก่อนแตะข้อมูลหลัก
node scripts/reseed-document-demo.cjs prepare

# สำรองและแทนที่ข้อมูลใน transaction เดียว
node scripts/reseed-document-demo.cjs apply "<absolute-path-to-new-manifest.json>"

# ตรวจชุดที่นำเข้าแล้วโดยไม่แทนที่เอกสารซ้ำ
node scripts/reseed-document-demo.cjs verify "<absolute-path-to-manifest.json>"
```

คำสั่ง apply ปฏิเสธเมื่อข้อมูลสำคัญเปลี่ยนจากตอน prepare และยืนยัน protected records ภายใน transaction ก่อน commit มีโหมด verify เพื่อกลับมาตรวจหลัง commit ได้โดยไม่ต้องนำเข้าซ้ำ ไม่ใช้ `server/prisma/seed.ts` ซึ่งล้างบัญชีผู้ใช้ด้วย
